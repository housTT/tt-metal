### Trace layer

- Persistent inputs, allocated before any capture (replicated over the two chips): per bucket `b` in 128, 256, 512, 1024 a token buffer `[1, b]` uint32, a chunk page table `[1, b/64]` int32, cos and sin tables `[1, 1, b, 64]` bf16 tile; shared across buckets a chunk-start tensor `[1]` int32 and the full page table `[1, 352]` int32 (320 blocks of the slot plus 32 spare blocks, see below). The output buffer per bucket is the tensor the first warm run of that bucket returned (same shape, dtype, layout and distribution as the captured body produces: `[1, 1, b, 5120]` bf16 tile, replicated after the norm's all-gather).
- `fwd[b]` (one trace per bucket): `Qwen36Model._forward_prefill_chunk_tp(tok, cos, sin, chunk_start, page_table, chunk_page_table)` with `model._chunked_chunk_size = b` (the upstream TP trace body, validated upstream at TP=4; `valid_len=None`, flexible chunked SDPA with the device chunk-start tensor, the vision `where` over the persistent merge buffers), then `model.norm(x, mode=PREFILL)` (the `DistributedNorm`: distributed RMSNorm on the fractured hidden, all-gather to the replicated full hidden) and `ttnn.copy` into the bucket's output buffer. The normalized hidden of every row is what the head needs, so the readout is inside the trace; after the replay the host reads the output buffer once (`ttnn.to_torch` with `ConcatMeshToTensor(dim=0)`, first replica).
- `save[slot]` and `restore[slot]` (one pair per snapshot slot): the 48 pairs of `ttnn.copy` between the live GDN state (`rec_state` fp32 `[1, 24, 128, 128]`, `conv_carry` bf16 `[1, 3, 5120]` per layer) and the slot's snapshot buffers (the stage 1 `_save_state` / `_restore_state` bodies).
- `zero`: `Qwen36Model._reset_gdn_state_for_new_sequence()` (TP: `reset_state_inplace` per GDN layer, copies from preallocated zero buffers).
- Per replay the host refreshes only the inputs that change: the padded token buffer, the chunk start, the slot's page table and its chunk slice, and the cos/sin tables for `[chunk_start, chunk_start + b)` from `model._rope_tp_cos_sin_torch` (the same host table the eager path uploads per chunk, so the M-RoPE of a media request is carried in the cos/sin values), through `ttnn.copy_host_to_device_tensor`; then `ttnn.execute_trace(mesh, fwd[b], cq_id=0, blocking=False)` and the readback. `engine.counters` records replays, host writes, readbacks and tower runs.
- Chunking: a state prefix `[0, S0)` (`S0` a multiple of 128) runs as full 1024 chunks followed by exact aligned pieces of the remainder (512, 256, 128 in descending order, `aligned_pieces`), so the GDN state that `save[slot]` snapshots never sees a padded row. A tail (schema plus the state remainder) and the full-sequence path run their last piece padded in the smallest bucket that fits: the attention and the GDN are causal, so the valid rows are unaffected, and the GDN state after a tail is never saved. The eager path runs the remainder as one padded chunk with the GDN valid-length mask, so the two paths differ by the bf16 rounding of a 128-boundary state carry on states whose `S0` is not a multiple of 1024 (the numbers are in "Replay correctness").
- Spare KV blocks: the traced path writes the KV of padded rows into the blocks after the valid rows. The KV allocation gets 32 spare blocks after the last slot and the traced full page table carries them, so a padded last chunk at the end of `max_len` has somewhere to write and the page table stays a multiple of 32 columns (the flexible SDPA otherwise pads it with a host-filled `ttnn.zeros`, which is a write and fails inside a capture: run 2 in the work log). Eager mode allocates no spare blocks.
- Warmup and capture order (`_setup_traces`): allocate the persistent inputs, allocate the DRAM guard (below), run every bucket body twice eagerly (the first run creates the output buffer, the second compiles the `ttnn.copy` into it), run the save and restore bodies for slot 0 and the zero body, `ttnn.synchronize_device`, `mesh.set_program_cache_misses_allowed(False)`, then capture `fwd[128..1024]`, `restore`/`save` per slot, `zero`. Program-cache misses stay forbidden for the lifetime of the engine, except inside the vision tower call (below). Trace region use is read from `ttnn.get_memory_view(mesh, BufferType.TRACE)` after the captures.

### Vision under tracing

- The merge is inside the trace: `_forward_prefill_chunk_tp` applies `ttnn.where(mask, vision, text)` over the persistent `_vis_buf` (`[1, 1, 1024, 5120]` hidden-sharded) and `_vis_mask_buf` (`[1, 1, 1024, 1]` replicated) that stage 2 allocated at engine build; for a bucket below 1024 the body slices them (warmed per bucket). Before each replay the engine stages the two buffers on the host (`_stage_merge`: the chunk's slice of the packed image rows placed at its `<|image_pad|>` or `<|video_pad|>` positions, and the 0/1 mask; a text chunk stages the zero mask), the same placement `Qwen36Model._set_vision_merge` does, from a host copy of the tower rows.
- The tower stays eager. In traced mode `_vision_request` first checks the request's `image_grid_thw` / `video_grid_thw` against the warm list (`check_warm_grids`; a grid outside the list raises `ValueError`, which the server returns as 422, and no tower program runs), then runs `get_image_features` / `get_video_features` with program-cache misses allowed (no miss can occur for a warmed grid), synchronizes, reads the `[N, 5120]` rows back to the host once (`ConcatMeshToTensor(dim=1)`), and frees the device rows, so no tower tensor is live during a replay. `StateHandle.vision.rows_host` keeps the rows for the schema continuation. At engine build (before any capture) the tower is run once per grid of `CLEF_VISION_WARM_GRID` (`;`-separated `t,h,w` list; required in traced mode, the engine refuses to start without it; the 8 reference images and the video are `REFERENCE_GRIDS` in `tt/engine.py`), which compiles the per-grid windowed-attention programs before the traces exist. Before the review the default was the same 7 reference grids and an unseen grid compiled after capture (open item 1 of the first version of this document, now the section "Why eager is the default").
- Conv kernel: with `valid_len=None` the upstream traced body runs the GDN causal conv through the fused KDA op (`ttnn.experimental.kda.qkv_causal_conv1d_silu`, `QWEN_GDN_CONV=kda`, the qwen36 default), while every masked bucket of the eager path runs the multiply-accumulate FIR conv (`gdn/tp.py` lines 284 to 290 and 532 to 548). The two kernels round differently, which at 64 layers moved the 16-record parity from max |dp| 0.072 to 0.108 and flipped the near-tie question `cfpb/5845071 issue` (work log, 13:18 and 13:27 ET). A traced engine therefore sets `QWEN_GDN_CONV=fir` before the model build (`os.environ.setdefault`; the eager masked path never reads it), after which the traced hidden rows are bit-equal to the eager rows on every bucket, padded or exact (`test_exact_buckets`, 4 layers), and the traced probabilities equal the eager ones (the 64-layer numbers are in "Replay correctness").
- The DRAM guard: tt-metal's trace intermediates are allocated at capture time and freed after it, and a later allocation that is live during a replay and overlaps those addresses is corrupted (`tech_reports/AdvancedPerformanceOptimizationsForModels/TraceCorrectness.md`, "Unsafe allocations"; program-cache buffers of a late compile share that address space). DRAM buffers are allocated bottom-up (`tt_metal/impl/buffers/buffer.cpp`: `bottom_up` defaults to true for DRAM). The engine therefore holds a 2 GiB replicated DRAM tensor (`CLEF_TRACE_GUARD_BYTES`) during warmup and capture, so every trace intermediate sits above it, and releases it afterwards, so later allocations (the per-grid tower compile of an image grid that was not warmed, the tower's own intermediates) fill the released range below the trace intermediates first. The engine logs the guard address and the address of a small allocation made right after the release (`trace_guard` in the engine and in the test JSON: at 64 layers the guard sat at per-bank address 2,717,329,344 and the probe landed at 1,131,500,992, below it). This is address-level reasoning, not something the trace allocation tracker can confirm: `tt_metal/impl/allocator/trace_allocation_tracker.cpp` (`record_allocation_if_unsafe`) records every allocation made while any trace is registered, whatever its address, so a tower compile for an unseen grid after capture is always reported as unsafe by the tracker, and the eager path run after capture likewise (work log, 13:01 ET: 69 program-cache buffers of the eager masked path). The tracker evidence below is therefore from a traced-only workload whose image grids were warmed before capture; images of other grids are served through the same traced path and rely on the guard (open item 1).

## Why eager is the default (stage 3 review P1, remediation 2026 Oct 05, 15:00 to 16:30 ET)

The review (`/home/hous/dev/clef/reports/review_stage3.md`, P1) found that the traced server compiled vision-tower programs for image grids outside its warm list while 13 traces were live, which the trace allocation tracker's rule reports as unsafe (`tech_reports/AdvancedPerformanceOptimizationsForModels/TraceCorrectness.md`, "Unsafe allocations": program-cache buffers share the address space with the trace intermediates), and that the 2 GiB DRAM guard was address reasoning, not a tracker-verified invariant. Orchestrator decision: the shipped default is the eager engine (`CLEF_TRACED=0`), which has no live traces and accepts any grid; tracing stays available as `CLEF_TRACED=1` for a deployment with a fixed set of image grids, with `CLEF_VISION_WARM_GRID` required, a 422 for every other grid and a 422 for more than one image or video grid per request (the second review's P2, "What the traced opt-in guarantees now"), so no vision program compiles with traces live. The cost of the decision is the 0 to 3 percent tracing gain of the timing table (one process, median of 5; the eager path is device-bound at 64 layers) and nothing else: the prefix planner now runs on the eager path too (below), and the eager probabilities equal the traced ones bit for bit ("Replay correctness").

### What the traced opt-in guarantees now

`CLEF_TRACED=1` requires `CLEF_VISION_WARM_GRID` (the engine raises at build without it, naming the reference grids), warms the tower on exactly those grids before any capture, and refuses every other grid at two places: the server returns 422 on the request thread from `image_grid_thw` / `video_grid_thw` before dispatch (`warm_grid_message`, fake-engine test `test_traced_server_refuses_grids_outside_the_warm_list`), and the engine raises in `_vision_request` before any tower op (device test above). The warm list is published in `/v1/models` as `traced_media.warm_grids` with the rule as `traced_media.rule`. The text path, the warmed grids and the replay-safety evidence of the traced engine are unchanged ("Trace allocation tracking"; the clean rerun of the traced-only suite with the current test file is in the work log, remediation entries). The DRAM guard stays in the code as a harmless default (`CLEF_TRACE_GUARD_BYTES`) and is no longer a safety argument.

One grid per request (second review, `/home/hous/dev/clef/reports/review_stage3_r2.md`, P2; remediation 2026 Oct 05, 17:40 ET onward): the per-grid refusal above left one way to compile with traces live. `tt/vision.py` `forward_with_taps` runs the tower once per grid row and, for more than one row, joins the outputs with `ttnn.concat(outputs, dim=2)`; the warm-up compiles one grid per call, so a request with two images (or two videos) of warmed grids would compile that concat program inside `_misses_allowed()` with the 13 traces registered. The traced opt-in therefore also refuses any request with more than one image or video grid, at the same two places: `Server.check_warm_grids` counts the rows of `image_grid_thw` plus `video_grid_thw` and returns 422 with `single_grid_message` before the warm-list loop (fake-engine test `test_traced_server_refuses_more_than_one_grid_per_request`: two images and two one-frame videos pass in eager mode with `image_grid_thw` of shape `[2, 3]`, and are refused with no engine call once the worker has a warm list), and `ClefEngine.check_warm_grids` raises on more than one row before any tower op. `/v1/models` `traced_media.rule` starts with the rule. Multi-image and multi-video requests stay fully supported on the shipped eager default (no live traces, `doc/vision/README.md` two-image record). Device evidence: `tests/test_engine_traced.py::test_two_grid_request_refused` on the 4-layer traced engine under `TT_METAL_TRACE_ALLOC_TRACKING=1 TT_METAL_TRACE_ALLOC_SKIP_PROGRAM_CACHE=0` sends two warmed grids in one `_vision_request`, then replays one 128-token `prefill_hidden`. ## Prefix planner (added 14:30 ET on the orchestrator's instruction; extended to the eager path in the review remediation)

`ClefEngine.plan_prefix(S, tail_len)` chooses the cached prefix length `S0` among the 128-aligned values from `(S // 128) * 128` down to one chunk lower, minimizing the predicted miss time (the prefix cost plus the padded chunk costs of the tail `S - S0 + tail_len`, from the measured per-bucket times of the engine's mode) and refusing any `S0` whose tail cost is higher than the default's, so a cache hit never gets slower; ties keep the largest `S0`. In traced mode the prefix cost is the exact-piece replay cost (`REPLAY_COST_S`: 128 0.173, 256 0.187, 512 0.220, 1024 0.338 s); in eager mode (since the review remediation) it is the padded-chunk cost of the eager masked buckets (`EAGER_COST_S`: 0.172, 0.191, 0.226, 0.345 s, the eager column of the timing table above), because the eager path runs the prefix as full 1024 chunks plus one padded remainder chunk and every masked bucket accepts any 128-aligned `chunk_start`. `CLEF_PLANNER=0` turns it off (the stage 1 rule `S0 = (S // 128) * 128`). It changes no trace and no numerics (every 128-aligned `S0` is a valid snapshot point and cached equals full for each: "Replay correctness" for traced, stage 1 `stage1_tt_text_l64_{cached,full}.jsonl` at max dp 0.0 for eager), and the server passes `tail_len=len(job.tail_ids)` when `prefill_state` accepts it. The chosen `S0` is stored on the handle, so the plan is made for the tail length of the request that filled the slot: a later hit on the same state with a longer schema can cross a bucket boundary that the default `S0` would not have crossed (example from the review: `S = 406` planned with a 558-token tail gives `S0 = 0`; a later 700-token tail then runs 1,106 rows as 1,024 + 128 where `S0 = 384` would run 722 rows in one 1,024 bucket). This is a performance effect only, bounded by one extra small bucket; correctness is unaffected. The decisions for the bench states are the same in both modes (host check in the work log, remediation entry): `S = 406` with a 558-token tail `S0 = 0`, `S = 2,227` with 562 `S0 = 2,048`, `S = 15,783` with 601 `S0 = 15,360`, `S = 1,371` and `S = 529` unchanged. Padding the prefix to the next bucket was not an option: the traced body has no GDN mask, so pad rows would enter the snapshotted GDN state. Predicted decisions are in the work log (14:25 ET). Measured on the server (14:35 ET, `/home/hous/dev/clef/reports/bench/p150x2_traced_planner/report.json`): the 370-token state 781.7 to 419.1 ms on a miss with the hit unchanged (424.8 to 419.5), the 2,200-token state 1,412.8 to 1,214.1 ms (hit 534.5 to 523.4), the 6-question short case 416.0 to 406.5 ms; answers unchanged (max |dp| 0.0 against the first server on the 16 text and 8 image records); cached equals full on the 4-layer suite with the planner active (`stage3_traced_l4_planner.json`).

Eager path (review remediation, 15:11 to 15:28 ET, work log): two eager servers, planner off then on, latency section of the bench and the 16-record text parity each (`/home/hous/dev/clef/reports/bench/p150x2_eager_planner{0,1}/report.json`). Planner off: 6 questions 416.8 / 414.3 ms, 370-token state 655.2 / 424.3, 2,200-token state 1,407.7 / 522.8 (new / cached). Planner on: 415.2 / 409.3, 424.2 / 416.9, 1,229.1 / 527.5. The planner takes 178.6 ms off the 2,200-token miss and 231.0 ms off the 370-token miss; hits and short cases move by at most 7.4 ms (inside the p95 minus p50 spread of 8 to 35 ms). ### Matmul program-config policy: not applied

Kev's `policy_linear` rebinds `ttnn.linear` to tuned 2D configs or `minimal_matmul` for the 9B shapes; it was worth 1.5 to 6.7x per matmul there because those matmuls ran at 5 to 7.5% of peak with the default (auto) config. The one plain `ttnn.linear` of weight (the MLP down projection, `1024 x 8704 x 5120` bf16 x bf16 HiFi2) already runs at 188 TFLOP/s per chip, 0.485 ms, and is 11% of the window; the only `SLOW`-flagged row is the `32 x 1056 x 5120` LM-head stub shape of the tail path (0.04 ms).
