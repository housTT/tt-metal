## Selection rule (written before any device run)

Verbatim from `scripts/dtype_sweep_summary.py` (`RULE_TEXT`):

> Eligible: complete text variants (status ok, ref16 and sweep200 rows present) with 0 argmax flips at reference top-2 margin >= 0.05 on the 16 reference records (CPU bf16 reference), sweep200 accuracy within 1.0 pp of baseline_stage1, and sweep200 mean dp within 0.005 of the best mean dp among the complete variants. Selected: the fastest eligible variant by the warm median device seconds per sweep200 record (eager, full path, bucket sequence seen before in the process). Ties within 2 percent of that time go to the fewer qwen36 changes, then the lower sweep200 mean dp, then the lower ref16 max dp. Reported, not gated: ref16 max dp against the 0.10 bar, near-tie flips, the fp32 comparison, the image sets (ref_image8, dev16_image, the sensitive record 7b7ef383). vision_upstream is an image-only control and never a selection candidate; the vision knobs of the selected config are the stage 2 values.

Definitions. A flip is an argmax change against the CPU bf16 reference on a question; it counts at margin when the reference's top-2 probability margin is at least 0.05 (the rule of stage 1 and of Kev's stage 4). "sweep200 accuracy" is `eval_metrics.score` over the 278 labelled questions (prediction: `choice` from the answer, `noul` at 0.5, `score` argmax). "sweep200 mean dp" is the mean over the 278 questions of the largest absolute option-probability difference against the CPU bf16 reference. "warm median device seconds" is the median of `timing.device_s` of `probs_for_request` over the sweep200 records whose bucket sequence (number of full 1024-token chunks and the bucket of the remainder) was seen earlier in the process, so program compiles do not count. A time tie is any eligible variant within 2 percent of the fastest. "qwen36 changes" counts the `qwen36` source changes a variant needs (`VARIANTS[...].qwen36_changes`): the GDN gate flag is one, the vision precision arguments are one, the engine-side projection override is zero.

Vision rule. The vision precision is not selected by this sweep: stage 2 selected `CLEF_VISION_PRECISION=accuracy` with `CLEF_VISION_ACT_BF16=1` on the tower PCC bars and the reference-set parity (`doc/vision/README.md`, gate statement after the amendment). `vision_upstream` reports the upstream precision on the same two image sets in the same harness as `baseline_stage1`, with the sensitive record `7b7ef383` as its own column, so the stage 4 review can see the delta per record. The selected config carries the stage 2 vision knobs.

CLEF_MAX_STATE rule. The default stays 16384 (Clef's own `max_length`). The summary records, for the selected variant, the largest `max_len` that fits 4 snapshot slots in the measured DRAM headroom at the selected dtypes (`context_contract` in `selected_precision_config.json`: `_fit_slots` arithmetic with the 2 GiB activation reserve, bf16 paged KV for the 16 attention layers, the GDN snapshot per slot). That number is a DRAM bound only; the release encoder caps a request at 16,384 tokens, so `CLEF_MAX_STATE` stays 16384 unless the orchestrator changes the request limit.

Expected outcome, stated before the run so the result can be judged against it: `baseline_stage1` reproduces stage 1 (ref16 max dp 0.0722, 0 flips, sweep200 accuracy near the CPU's 80.9 percent); `gate_fp32_off` fails the flip rule (stage 1: one flip at margin 0.0513); `down_bfp8` is the only candidate that can be faster than the baseline; `proj_bf16` and `all_hifi4` are slower and are kept only if they buy agreement. If `down_bfp8` is eligible it is selected; otherwise the baseline stays.

## The `QWEN36_GDN_QKV_FP32` flag (stage 4 amendment to the plan)

Files: `/home/hous/dev/clef/tt-metal/models/demos/blackhole/qwen36/tt/gdn/tp.py` (+75/-15) and `/home/hous/dev/clef/tt-metal/models/demos/blackhole/qwen36/tt/model_config.py` (+1); test `/home/hous/dev/clef/tt-metal/models/autoports/cloudflare_clef/tests/test_gdn_qkv_fp32.py`; row dump `/home/hous/dev/clef/reports/stage4_gdn_rows_qkv_fp32_off_T8192.pt`.

What the fused chunk op accepts, read from the source before the change:

| Source | Fact |
|---|---|
| `ttnn/cpp/ttnn/operations/transformer/chunk_gated_delta_rule/device/chunk_gdn_device_operation.cpp` lines 41 to 43, 58 to 59 | the device op validates `q`, `k`, `v` as `BFLOAT16` and `g`, `beta`, the constants and the initial state as `FLOAT32` |
| `ttnn/cpp/ttnn/operations/transformer/chunk_gated_delta_rule/chunk_gated_delta_rule.cpp` lines 39 to 43, 181 to 190 | the host wrapper casts any non-bf16 `q`, `k`, `v` to bf16 and any non-fp32 `g`, `beta` to fp32 before the device op ("GPU-style mixed precision: q/k/v are bf16 (gate/decay and state stay fp32)") |
| `.../device/chunk_gdn_phased_program_factory.cpp` line 210 | the prep kernel's `q`, `k`, `v` circular buffers are `Float16_b` |

So the kernel does not reject fp32 `q`, `k`, `v`: it casts them back to bf16, and a cast after the conv is a bit-exact round trip with no effect. The op already takes `beta` in fp32 (cast from the bf16 sigmoid output today). Under this contract the flag changes the two computations before the op whose precision is not fixed by the op: the causal FIR conv with its SiLU (`models/experimental/gated_attention_gated_deltanet/tt/ttnn_gated_deltanet.py` lines 220 to 240: four taps, `ttnn.multiply` then `ttnn.addcmul`, every output bf16 today) and the beta sigmoid. With `QWEN36_GDN_QKV_FP32=1`:

- `load_gdn_weights_tp` loads fp32 copies of the four conv taps (`tw["conv_taps_f32"]`, exact: the checkpoint taps are bf16 values).

- `forward_prefill` takes this arm instead of the KDA conv op or the bf16 FIR whenever the flag is on (the KDA op is bf16 by construction); `forward_prefill_batched` the same with its DRAM memory config. - `ClefEngine._device_dtypes()` reports `gdn_qkv_fp32` and `gdn_conv_taps`, so every sweep JSON and engine log shows the state of the flag.
