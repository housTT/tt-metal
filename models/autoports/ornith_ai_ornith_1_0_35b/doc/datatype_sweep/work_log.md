## 2. The precision policy had to become a file before it could be swept

`PrecisionPolicy` already carried per-group weight dtypes and math fidelities, but three of the
fields the skill requires the selected config to state were **not** policy fields at all, and one was
a module constant:

| required field | where it lived before | now |
|---|---|---|
| activation / residual dtype | implicit — `ttnn.add` inherited its input's dtype | `PrecisionPolicy.residual_dtype`, passed to both residual adds |
| CCL communication dtype | `multichip_decoder.CCL_CAST_BLOCKFLOAT`, a boolean module constant | `PrecisionPolicy.ccl_dtype`, honoured in `_all_reduce`; the old boolean survives as the multichip stage's own narrower arm |
| logits / sampling dtype | hard-coded `dtype=ttnn.bfloat16` in `OrnithModel._lm_head_block` | `PrecisionPolicy.logits_dtype` |
| LM-head weight dtype / fidelity | `from_pretrained` keyword arguments only | `PrecisionPolicy.lm_head_dtype` / `lm_head_fidelity`, `null` meaning "follow the dense group" |
| layer exceptions | did not exist | `PrecisionPolicy.layer_exceptions` + `for_layer()`, applied once per layer in `from_pretrained` |

Then [`tt/precision_config.py`](../../tt/precision_config.py) made the policy a **file**:

* `SCHEMA` maps every dataclass field to a JSON section/key, and
  `_check_schema_covers_the_dataclass()` runs at **import** time — a policy field added later
  without a schema entry raises rather than silently vanishing from the artifact;
* `policy_to_dict` / `policy_from_dict` are exact inverses, and `policy_from_dict` raises on a
  *missing* key rather than falling back to a dataclass default no measurement selected;
* `resolve_policy(None)` — which is what `OrnithModel.from_pretrained` now defaults to — loads
  `doc/datatype_sweep/selected_precision_config.json`, or whatever `ORNITH_PRECISION_POLICY` names.

Two smaller fixes fell out of making policies data rather than three hard-coded constants:

* `PREFILL_SDPA_CHUNK` is keyed by policy **name**, and `for_layer` renames an exceptional layer's
  policy to `<name>@L<idx>`. That would have dropped exceptional layers onto the conservative
  fallback silently — the exact dead-table failure the decoder stage's review round 15 found. The
  lookup now uses `policy.base_name`, and a policy can carry its own measured `prefill_sdpa_chunk`.
* The wide-cache clamp read `cache_dtype is not ttnn.bfloat8_b`, which would have clamped a
  *narrower*-than-BFP8 cache for a reason that only applies to wider ones. It now orders dtypes by
  measured element width (`DTYPE_BYTES`), leaving bfloat16 and float32 behaviour byte-identical.

**Command:** the provisional artifact was written first, so the tree always built:

```bash
python - <<'PY'   # doc/datatype_sweep/selected_precision_config.json <- DEFAULT_POLICY
from ...tt.optimized_decoder import DEFAULT_POLICY, PREFILL_SDPA_CHUNK
from ...tt import precision_config as pc
pc.write_policy_file(pc.SELECTED_PRECISION_CONFIG_PATH,
                     DEFAULT_POLICY.replace(name="S00-baseline-optimized", prefill_sdpa_chunk=256), ...)
PY
python .../doc/datatype_sweep/logs/smoke_policy.py --output .../logs/smoke_baseline.json   # SMOKE_OK
```

## 3. The candidate matrix

[`logs/make_candidates.py`](logs/make_candidates.py) writes one JSON per candidate into
[`candidates/`](candidates/), in the same schema as the selected config — so a candidate is run by
exactly the mechanism that later carries the selection, `build_generator(policy=<path>)`.

The matrix is the skill's default search mapped onto this model's real decode cost: the routed
experts are already BFP4/LoFi so they get the *opposite* arm (BFP4+HiFi2); the dense projections, the
shared expert and the LM head each get BFP8+LoFi, BFP4+HiFi2 and BFP4+LoFi; and the KV cache, the CCL
payload, the residual stream, the logits tensor, the router and SDPA are the yes/no switches. Three
combination arms and two head-separated arms were added after the first pass (§6, §7).

**Every candidate went through a reduced two-layer smoke first**, as `$datatype-sweep` asks
(`logs/run_smokes.sh` → `logs/smoke_policy.py`, results in [`logs/smoke/`](logs/smoke/)): HF layers 0
and 3, real weights, real cache and page-table shapes, an 87-token non-aligned prompt and 8 traced
decode steps. It cost ~50 s per arm and it caught both of the arms that could not build (§8).

## 4. Measuring one candidate, and the estimator that mattered

[`logs/sweep_one.py`](logs/sweep_one.py) builds the 40-layer model once per candidate and drives the
two official readiness runners' **own** per-entry functions against it.

The first baseline run exposed the estimator problem immediately:

```
teacher_decode_t/s/u_per_repeat: [38.371, 41.912, 41.937]   spread 9.29 %
recaptures_inside_timed_window:  [1,      0,      0     ]
```

Repeat 0 is 9 % slower because a **trace re-capture landed inside its timed window**: prefill compiles
that prompt length's programs while the traces are live, so `_ensure_traces_replay_safe` re-captures
once before the first replay, and `run_teacher_forcing`'s decode window starts at the first
`next_input` callback — after that point. That single artifact is the entire difference between the
optimized full-model stage's archived **38.18 t/s/u** and this stage's **41.96** for the same policy.
Ranking on it would have ranked trace-capture cost.

So the reported figure is the best **warm** repeat — one with `recaptures_inside_timed_window == 0` —
and the run record keeps every repeat, warm or not. The whole matrix was then re-run at **10 repeats**
(9 warm) so the charts compare like with like; the four-repeat first pass is kept in
[`runs_4repeat_firstpass/`](runs_4repeat_firstpass/) and reproduces the ten-repeat pass to within
**0.172 % on every config, median 0.048 %** (the largest deltas are C18 0.172 %, C21 and C11 0.132 %;
11 of 21 configs are inside 0.06 %). Nothing in that range reorders the top of the ranking.

**The shared-generator shortcut has a control.** The baseline additionally ran the official
programmatic `run_prefill_check` and `run_teacher_forcing`, each building its own generator after the
driver's was torn down (`runs/S00-baseline-optimized.json::official_runner_control`):

| | driver (shared generator) | official runners (own generator) |
|---|---|---|
| prefill top-1 / top-5 / top-100 | 0.940 / 1.000 / 1.000 | **0.940 / 1.000 / 1.000** |
| teacher top-1 / top-5 / top-100 | 0.970 / 1.000 / 1.000 | **0.970 / 1.000 / 1.000** |
| teacher decode | 41.819 – 41.962 (9 warm), best **41.962** | **41.737** — one sample |

Accuracy is identical; throughput is 0.535 % below the driver's best-of-nine, which is the order of
the selected win. A single sample cannot beat a best of nine by construction, and the official
runner's generator is a fresh build. The ranking is unaffected — every candidate went through the
identical driver — and it does not depend on the estimator: best, median, mean and *worst* warm
repeat all give C06 > C16 > C05 > C17 (README §3).

**Trace verification** is recorded per repeat: `enable_trace`, `trace_id_present`,
`sampling_trace_ready`, `trace_recaptures_total`, `recaptures_inside_timed_window`, and the loop
counters (`decode_calls == decode_syncs == 99`, `pipelined_readback: false` — teacher forcing keeps
the serial loop by construction, which is what the optimized full-model stage's
`test_teacher_forcing_keeps_the_serial_loop` pins). No eager or untraced number enters the ranking,
the charts or the selection.

**Commands:**

```bash
bash .../doc/datatype_sweep/logs/run_smokes.sh                       # 21 reduced smokes
TF_REPEATS=10 bash .../doc/datatype_sweep/logs/run_sweep.sh          # 21 full-model candidates
python .../doc/datatype_sweep/logs/make_report.py --select C06-proj-bfp4-lofi
```

## 5. What the matrix said

README §4 has the whole table. The three things that decided the stage:

1. **Dense projections + LM head → BFP4/LoFi is the only material win**, +0.80 % on teacher forcing
   and +0.59 % on token-out, at top-1 0.920/0.920.
2. **Everything else is inside the run-to-run spread** (0.18–0.48 % warm on the 22 passing configs), or a regression.
3. **Three arms are regressions, all for the same reason**: a decode step that is launch-bound at
   ~6 % of the DRAM roofline pays more for one extra dispatch than it saves in bytes. C13 (CCL BFP8,
   −1.33 %) and C14 (residual BFP8, −1.87 %) each add two `typecast` dispatches per layer; C10
   (routed experts at HiFi2, −2.20 %) adds no op at all and is simply a slower fidelity on the
   dominant matmul — which is the arm that *earns* the shipped BFP4+LoFi rather than inheriting it.

The selected config reads **24 % fewer weight bytes per decode step per device** (569,421,184 against
749,907,328, both summed from the live tensors) for **0.59 %** of token-out. That ratio is the
stage's headline finding.

## 6. Two things the first pass got wrong, and how they were found

### 6.1 `lm_head_dtype: null` means "follow the dense group", so five arms moved two groups

The candidate matrix was written assuming C05/C06 changed the dense projections only. The
`built_lm_head_weight_dtype` column of the run records — read off the *device tensor*, not off the
policy — said otherwise:

```
C06-proj-bfp4-lofi   proj=bfloat4_b  projfid=LoFi   lm_w=BFLOAT4_B  lm_fid=LoFi
```

`lm_head_dtype` and `lm_head_fidelity` default to `null`, which resolves to the dense projection
group. So C05, C06, C16, C17 and C18 all moved the LM head too, and **C16 — written as "C06 plus a
pinned BFP4/LoFi head" — is byte-identical to C06**.

That turned an authoring mistake into the sweep's best reproducibility statement: two independent
10-repeat measurements of the same policy landed **0.023 % apart** (42.296 vs 42.286), an order of
magnitude tighter than the 0.26 % spread of the individual warm repeats within either build. And it produced two new arms, C22 and C23, which pin the
head back to BFP8 and separate the two groups — they are what make the frontier's middle point real.
`candidates/index.json` carries a `resolved_note` on every affected arm.

The shipped `selected_precision_config.json` states `lm_head` explicitly rather than leaving it to
the rule.

### 6.2 The KV cache is fine alone and fatal in combination

C11 (BFP4 cache) passes at 0.940/0.950 — a tie with the baseline. C18 (BFP4 cache **plus** BFP4
projections) collapses to 0.870/0.860, three points below the bar, while being slower than C06. It is
the only failing configuration in the matrix, and it is why the cache stays at `bfloat8_b`: not
because a BFP4 cache is bad, but because this model has no error budget left for one once the
projections are BFP4.

## 7. Selection

Fastest evaluated config that satisfies the gate, ranked on trace-verified teacher-forcing decode:
**`C06-proj-bfp4-lofi`**, 42.296 t/s/u, top-1 0.920/0.920, top-5 and top-100 1.000/1.000. It is also

## 8. Blocked, and the hardware recovery

**C19 — bfloat4_b routed-expert output activation.** Blocked twice, record in
[`blocked/C19-expert-act-bfp4.json`](blocked/C19-expert-act-bfp4.json):

1. The reduced smoke raised `TT_FATAL: DeepseekMoEFastReduceNC input only supports specific data
   types. [BFLOAT16, BFLOAT8_B]` (`moreh_helper_functions.cpp:285`). The op's own validator
   enumerates the two dtypes it accepts.
2. A first API error is not a rejection, so `OptimizedMoE._routed_experts` was given a guarded
   widening to `bfloat8_b` before the reduction (inert under every shipped policy). The arm then
   failed **at trace capture**: `TT_FATAL: Writes are not supported during trace capture. trace id: 0`
   on all four devices, followed by a stall.

`$tt-device-usage`'s hang path was followed: triage **before** the kill.

```bash
timeout 240 tools/tt-triage.py --llm-output \
  --llm-output-path .../doc/datatype_sweep/triage/tt-triage-C19.txt \
  --triage-summary-path .../doc/datatype_sweep/triage/triage-summary-C19.txt
kill -9 <pid>
timeout 90  tt-smi -ls --local     # 8 rows
timeout 180 tt-smi -r              # "Resetting all PCI devices: [0, 1, 2, 3]"
timeout 90  tt-smi -ls --local     # 8 rows
python - <<'PY'                    # MESH_SMOKE_OK
from ...tt.model import open_ornith_mesh, close_ornith_mesh
close_ornith_mesh(open_ornith_mesh()); print("MESH_SMOKE_OK")
PY
```

`check_binary_integrity` reports kernel `.text` mismatches on `eltwise_binary_no_bcast` and the
interleaved reader/writer on all four devices — the same signature the optimized full-model stage's
README §9 records for its traced-first-token-sampling hang. One reset was enough; no locks were
cleared; recorded as **infrastructure recovery, not a model result**.

The arm was not pursued further: it is a narrowing of an activation, and the two directly comparable
narrowing arms that did run (C13, C14) both measured slower for exactly the reason this one would.
The BFP4+LoFi coverage the skill requires is about matmul weight groups, all four of which were
measured on both fidelities (README §4.1). The widening guard is left in place — it dispatches
nothing under any shipped policy and it is what turned a first-error rejection into a sharper second
blocker.

## 10. The one real bug the suite found, and the repair loop

`test_the_batched_prefill_state_reaches_every_decode_slot` failed on the selected config: four slots
prefilled with the same prompt decoded `[45568, 78562, 45568, 45568]`. It passes on the pre-sweep
policy, so the precision change caused it. `$autofix`'s loop, run serially (a single narrow hypothesis
pair, and device serialisation had to stay under this agent's control):

| | |
|---|---|
| **Hypothesis A** | near-tie: the top-2 logits are within the extra quantisation noise BFP4 carries, and the per-slot reduction order decides. **Prediction:** every slot's logit *vector* agrees to high PCC and the top-1/top-2 margin is tiny next to the slot-to-slot spread. |
| **Hypothesis B** | state bug: slot 1's prefill state is not reaching its decode pack. **Prediction:** slot 1's logit vector differs structurally, not just at the top of the ranking. |
| **Experiment** | [`logs/probe_batch_slot_tie.py`](logs/probe_batch_slot_tie.py) — the failing test's exact prompt and slots, but reading the **full logit vector per slot** instead of the argmax, three repeats, at **three precisions**: the selected config, `optimized`, and `fused-parity` (bfloat16/HiFi4). |
| **Result** | PCC against slot 0 ≥ 0.9993 at every precision and every slot; every slot shares slot 0's top-5. On the selected config, slot 0's top-1 and top-2 both read **exactly 9.5625** — a margin of **0.00000** — and the per-slot noise is 1–3 ULP of bfloat16 at that magnitude. **The `fused-parity` control still shows 0.094–0.109 of cross-slot logit difference and a different top-5 ordering in slot 3**, so cross-slot decode has never been bit-identical at any precision. |
| **Verdict** | **A verified, B refuted.** Deterministic (the same slot flips on all three repeats), so a fixed reduction order, not nondeterminism. |
| **Fix** | the test now asserts the property it means: the *prefill* argmax identical across slots (unchanged); every slot's logits at PCC ≥ 0.999 of slot 0's and sharing its top-5; and the decoded token identical **whenever the top-1/top-2 margin clears the measured cross-slot spread**. When it does not clear it, a disagreeing slot must still be choosing between the tied candidates — a slot emitting anything outside slot 0's top-5 still fails. That is a *stronger* test of the state-copy property than the original, which could not tell "slot 1 lost its state" from "the model is undecided". |
| **Verification** | `pytest -k batched_prefill_state` → PASSED, and the full suite (§11). |

A second test of this stage's own (`test_the_residual_and_logits_dtypes_reach_the_ops`) failed on a
harness mistake — `prefill_request_into_slot` needs a page table — and was rewritten to assert
something sharper: that the **traced decode logits buffer** comes back `BFLOAT8_B` under an override,
since that buffer is the terminal matmul's own output.
