# Watcher log classification — fused decoder

The committed `watcher_log.txt` is the log of a single watcher-enabled run of the fused decoder's
state- and trace-critical test subset. It is classified here so "the log is clean" is a checkable
claim rather than an impression: every line falls into exactly one bucket, the buckets sum to the
file's line count, and a fatal-class regex over the whole file returns zero matches.

`census.py` reproduces both the census and the grep into `census_summary.txt`; the table below is
transcribed from that file.

That filter is **copied from `logs/run_evidence.sh`**, which is the one place it is defined; run
the pipeline rather than this block if the two ever disagree. Review round 16 found this file

`TT_METAL_WATCHER_APPEND=1` matters: watcher truncates its log on each device open, so without it
the committed log would hold only the last test's session instead of all of them.

## Fatal-class grep

`census.py` greps the whole log for watcher errors/asserts, out-of-bounds accesses, invalid NOC
coordinates or addresses, L1/stack overflow, sanitizer reports, corruption, and hang/deadlock
markers. The result is **0 fatal-class matches**, reproduced into `census_summary.txt` as
`fatal-class matches: 0`. There are no suspected false positives to explain.

## What the periodic dumps contain

How much these dumps carry varies with the run. Watcher's *periodic* dump fires on a timer, so
whether it ever catches a kernel resident — and therefore whether `kernel_names.txt` holds real
kernel paths or only the single `blank` entry, and whether any stack-usage watermark is recorded —
depends on timing, not on the code under test. `census.py` classifies whatever is there and says so
explicitly, including reporting a *missing* stack-usage summary as missing rather than as "no
overflow"; `census_summary.txt` is the record for any given run. Earlier revisions of this section
asserted one outcome or the other and went stale the next time the subset or the timing changed,
which review rounds 16 and 18 both caught.

Independently of the dumps, watcher's inline instrumentation — NOC address/coordinate checks, CB
bounds, asserts, sanitizers — runs on every kernel launch throughout, and it is that
instrumentation the fatal-class grep above is reading.

## Stack-usage summary

Watcher only prints one for dumps where the firmware recorded a watermark, which is a property of
when the periodic dump fires rather than of the code under test — so a given run may or may not have
any. `census.py` classifies whatever detail and summary lines are present and reports the **minimum
headroom across them**; when there are none it says so explicitly
(`stack headroom: not reported in this log (no 'bytes free' lines)`) rather than treating the absence
as "no overflow". `census_summary.txt` carries whichever applies to the committed log, and README §7
quotes it from there. Stack overflow would also surface through the fatal-class grep, which is
clean.
