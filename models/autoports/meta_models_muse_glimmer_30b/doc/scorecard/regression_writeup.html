Muse-Glimmer Concurrency Regression

A prefill batch's page table was indexed by device slot instead of by row. Under concurrent arrivals every request but the last wrote its KV through the last request's blocks. Fixed; verified at concurrency 32.

Reply lengths are the model's own reasoning length: with the fix they no longer depend on concurrency (47% at conc 8 vs 42% at conc 32, against 25% at conc 1 vs 62–77% at conc 32 before), every reply reaches an answer, and the parser-on content lengths match August to within a few percent.

Root cause: generator.prefill_forward indexed the prefill page table with each request's device slot. The vLLM plugin builds that table with one row per prefilling request and hands slots separately. The moment any request is already decoding, a new batch's slots exceed its row count; normalize_page_table aliases the overflow onto the last row, so those users write K/V through the last user's blocks. Last writer wins. Fix: index by batch row; slot steers sampler state only.

Why it looked bimodal

A burst that lands in one engine step is clean. A burst that straddles two steps collapses. Arrival timing decides.

The first step's requests get slots 0…k−1 that equal their rows. Requests arriving one step later get slots k…N−1 against a table with only N−k rows. Thirty near-simultaneous HTTP requests split across steps unpredictably, so identical runs scored 86.7% or 3.3%. The August release plugin carries the same slot machinery; its 90.0% was a lucky landing, which is why the August artifact reproduces the failure today.

The fix

-  logits, row_in_tile = self._prefill_user(ids, user_id=slot, page_table=table, start_pos=starts[user])
+  logits, row_in_tile = self._prefill_user(ids, user_id=user, page_table=table, start_pos=starts[user])
  • Three call sites in tt/generator.py: user_id=slot → user_id=user. The slot still reaches apply_prefill_sampling_state, which is the only thing it legitimately steers.
  • A permanent guard: the blocks a prefill batch writes must be disjoint across rows. Prefix-cache hits share their cached prefix and never write it, so only the range from start_pos onward is checked.
  • Regression test test_batched_prefill_indexes_the_page_table_by_row_not_slot: same two prompts, same two-row table, prefilled with slots [2, 3] vs None; first-decode host logits must be identical. Fails before, passes after.

The same user_id = empty_slots[i] pattern appears in models/demos/deepseek_v3/tt/generator_vllm.py:165. Not examined here.

What was wrong on the way here

Eight hypotheses were “ruled out” on single 30-problem runs of a bimodal metric. None of that was evidence.

The measurement that found the bug was a 20-second probe on first tokens only — 150–240 samples per arm instead of one noisy score per hour. Things that were tested properly and are innocent: the on-device sampler (0.771 vs 0.740 host, ~96 trials each), the plugin build, the kernel cache, the tt-metal binaries, the weights, the rendered prompt, device reset, and the layer math (194 PCC checks bit-identical to baseline). Prefix caching was never the cause; it only exposed the guard's first draft.

Status of published numbers

Every eval score currently on the tt-hous/muse-glimmer-30b model card was measured with this bug live at concurrency 16–32. They describe the failure, not the model. The package needs rebuilding from the fixed code and re-evaluating before it carries scores or a concurrency-32 serving profile.
